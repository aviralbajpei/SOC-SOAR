Governed agentic AI for SOC alert triage

Five AI agents assemble the evidence behind every security alert. Code scores and routes it, and a human analyst approves anything with real impact. Every step is recorded.

One case through the pipeline: ALRT-3001, suspicious login by a privileged user on a critical server

  1. AAlert validated and screened
    No injection found; personal data masked
  2. AEvidence assembled
    Threat intel, asset register, identity and history lookups
  3. AFour agents assess the case
    Correlation, threat intel, asset context, risk; every claim cites an evidence ID
  4. AScored 97, critical
    Critical asset with malicious intel, and privileged multi-stage activity, set the floor
  5. EEscalated to the incident response lead
    SLA watcher re-escalates if it waits more than 10 minutes
  6. HTier 1 approval refused; SOC Lead approves
    Authority is checked on the server, not in the browser
  7. AAllow-listed action recorded
    Simulated in the prototype; full audit trail kept

The problem

A security operations centre receives more alerts than its analysts can investigate. Each alert needs related events, threat intelligence and asset context gathered from separate tools before anyone can judge it. The judgement itself varies between analysts and shifts, and approvals often happen by phone or chat with little record.

~960alerts a day in the median SOC
~40%of alerts never investigated
~70 minto fully investigate one alert

Survey of 282 security leaders, reported by The Hacker News, September 2025.

How we chose the opportunity

We used critical and systems thinking to find the root cause: evidence assembly is manual and fragmented. We then used STOIC prompts (situation, task, objective, inputs, constraints) to generate eight ideas and scored each for usefulness, realism and feasibility. The AI ranked an auto-enrichment evidence card highest and suggested pairing it with a verdict scorer; we built that pairing as multi-agent triage with human approval, and kept containment out of the AI's hands.

From manual triage to governed agents

In the redesigned process every activity is marked Aautonomous, Hhuman-in-the-loop or Eescalation. Routing is decided by code, never by a model.

Architecture

The system runs fully online. The analyst works in a Streamlit console hosted on Streamlit Community Cloud; it calls seven n8n workflows on n8n Cloud over HTTPS, and the agents call open-weight models through the Groq API. Cases and the audit log are stored in n8n Cloud data tables. The guardrails sit in code between the workflow and the models, so a model cannot talk its way past them.

Model comparison

Each model received the same five alerts, prompts, evidence and output schema, three times each: 15 runs per model, scored automatically against an expected outcome for every alert.

Key findings

No model missed an attack. All three had zero false negatives; every mistake went to the safe side, a case sent to a human, never a real attack closed.

Code protects against a weak model. GPT-OSS 120B proposed the right class only 33% of the time, yet its final class was right in every run, because code computes the score from the evidence.

GPT-OSS 20B is fastest but less reliable. It invented evidence IDs six times; the guardrail caught every one and sent those cases to a human, which lowered its task completion to 60%.

Qwen 3.8 27B, a preview model, was throttled on the free tier: 9 rate-limited calls and two time-outs.

Recommendation: GPT-OSS 120B for a pilot. It had the best routing (87%), the most reliable structured output (98% valid JSON on the first try) and the highest task completion (87%).

What we measure

  • Classification: exact match, and within one level, of the final class
  • Escalation accuracy: high-risk cases escalated, benign ones not
  • False positives and negatives: unnecessary escalations, and missed ones
  • Hallucination: evidence IDs cited that do not exist
  • Structured output: valid JSON on the first attempt (provider throttling excluded)
  • Latency: median model time per case
  • Task completion: case reached the designed end state
  • Explanation quality: blind 1–5 scoring by two team members

Expert validation

Limitations and next steps

Limitations

  • Five synthetic alerts show the controls work, not accuracy at scale.
  • Injection screening uses known patterns and can be paraphrased around.
  • Analyst identity comes from a selector, not real sign-in.
  • The audit table is append-only by design, not tamper-proof.
  • Hosted models receive masked, synthetic alerts; real data would need local models or a data-processing agreement.
  • The cloud deployment uses free tiers (n8n Cloud trial, Streamlit Community Cloud, Groq), so runs can be throttled and the console sleeps when idle.

Recommended next steps

  • Pilot in shadow mode on real alerts, with expert-set thresholds.
  • Connect to a live SIEM (for example Wazuh) and single sign-on.
  • Forward audit events to the SIEM or write-once storage.
  • Add a classifier-based injection screen.
  • Feed analyst decisions back into detection tuning.
